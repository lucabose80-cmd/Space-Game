## Praxis-Learnings
1. **Antigravity-Cloud-VM Bildgenerierung (2026-11-28):** `generate_image` meldete `resource_exhausted` (Quota für `gemini-3.1-flash-image` erschöpft) und `npm run art:gen -- --check-key` fand keinen Key. Lösung: `titleBg` in `CUTSCENE_OPTIONAL_SPRITES` registrieren + `P3-55` in `SPRITE_QUEUE.md` eintragen, und bis zur Lieferung den Live-Canvas-Backdrop auf Basis von `cutscene_bg_solaris*.png` + animiertem Schiff/Sternenfeld nutzen. Sobald `public/art/sprites/title_bg.png` liegt, wird es ohne Code-Änderung automatisch bevorzugt.
2. **Bestehende Playwright-Tests:** Zahlreiche Tests (`t3`, `t4b`, `t4c`, `m10p*`, `m10cp*`) blenden den Startscreen direkt via `document.getElementById('title-overlay')?.classList.add('hidden'); g.ui.titleVisible = false;` aus. `#title-overlay`, `#btn-continue` und `#btn-new-game` bleiben als IDs erhalten; neue Tests müssen für automatische Erkennung durch `tests/run.cjs` mit `t<N>` beginnen (`t9_title_screen.cjs`).
3. **Backdrop-Zoom & Schiffs-Ausrichtung:** Beim Verschieben von `cutscene_bg_solaris` nach rechts (`panX = 24`) braucht der Zoom mind. `1.16`, sonst entsteht links eine sichtbare Kante. Die Schiffs-Sprites zeigen standardmäßig nach oben (`-90°`), daher braucht Anflug nach oben-rechts positive Rotation (`+0.54` bis `+0.72 rad`).
4. **Cloud-Login auf frischem Gerät:** `firebaseService.onAuthChange` lud früher nur bei `isCloudSaveAhead(...)`; mit `!this.state.hasSave() || isCloudSaveAhead(...)` wird auch ein Tag-1-Cloud-Spielstand beim Login am Startscreen zuverlässig auf ein neues Gerät heruntergeladen.
3. **Spielstand-Slots (2026-11-28, Claude-Chat):** 3 Slots (`GameState.activeSlot`, `switchSlot`, `clearSlot`, `peekSlot`; Schlüssel Slot 1 = alter `starlighter_save_v2`, Slot 2/3 = `…_slot2/_slot3`, aktiver Slot in `starlighter_active_slot`). **Cloud nur Slot 1:** Guard in `GameState.save()`, `firebaseService.scheduleAutoSync/syncAllToCloud`, Abgleich `Main.reconcileCloud` (auch beim Slot-Wechsel auf 1). **Falle:** Slot 1 leeren würde die Cloud zurückholen (`!hasSave()` → Import) → „Slot leeren“ nur für 2/3, Slot 1 zurücksetzen nur per „Neues Spiel“ (überschreibt Cloud, mit Warntext). `switchSlot` speichert nie. Test `t10_save_slots`. Prüfpunkte: `ABNAHME.md` Block J. Nicht gemacht: Slots in der Cloud (bräuchte Firestore-Regeln/Datenmodell), Slot-Wechsel im laufenden Spiel (nur am Startscreen).
4. **Slots in der Cloud + Planeten-UI (2026-11-28):** Slot 2/3 als Felder `slot2Json/slot3Json(+UpdatedAt)` im selben Dokument `saves/{uid}` (Regeln erlauben beliebige Felder → kein Rules-Deploy). `syncAllToCloud` schreibt für Slot ≠ 1 nur diese Felder (keine Bestenliste/Wochen-Prüfung); `downloadCloudSave(slot)`, `downloadAllCloudSlots()` (füllt lokal leere Slots still nach Login auf, `GameState.writeSlotRaw`), `deleteCloudSlot()` (leert Feld bei „Slot leeren“). `switchSlot` ruft vorher `flushAutoSync` (sonst ginge die letzte Änderung des alten Slots verloren; `syncAllToCloud` liest Slot + JSON synchron vor dem ersten `await`). `reconcileCloud` verwirft die Antwort, wenn der Slot inzwischen gewechselt wurde. UI: `.ts-constellation` (absolut über der Key-Art, Planeten per CSS-Gradient, Positionen `.ts-slot-star.s1/s2/s3` in %; unter 720 px Reihe im Fluss). Tests `t10_save_slots`, Screenshot `tests/out/title_slots.png`. Nicht gemacht: Lösch-Marker gegen Wiederauferstehung über zweites Gerät, echte Planeten-Sprites.
