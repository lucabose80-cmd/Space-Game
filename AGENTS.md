## 1. Project Snapshot (v1.4 — Milestone 10-C implemented, M11 in progress)
- **Game:** **STARLIGHTER** — Cozy Retro-Sci-Fi Action-RPG & Space-Shop browser game inspired by *Moonlighter 1*.
- **Stack:** `TypeScript` (strict) + `Vite 8` + custom HTML5 Canvas 2D engine (`960×540` HD pixel-art buffer at `RENDER_SCALE = 2` over `480×270` logical coordinates) + Web Audio procedural synth + Firebase Auth & Cloud Firestore (`starlighter-15b1f`).
- **Deployment:** Pushing to `main` triggers automatic Vercel deployment. **Never** tell the user to open a `localhost` URL.
- **Language:** All in-game UI text, toasts, item names, and user-facing responses are in **German**.

## 3. Non-Negotiable Rules (Do & Don't)
1. **Zero-Dungeon-Credits Rule:** **NEVER** add `state.credits +=` inside `src/scenes/DungeonScene.ts` or anywhere under `src/dungeon/` (`enemyAi.ts`, `dungeonRenderer.ts`, `mechanicsGen.ts`, `roomMechanics*.ts`). Verify with `rg -n "state\.credits\s*\+=" src/scenes/DungeonScene.ts src/dungeon/` → 0 hits. Credits are earned exclusively through selling relics in *Astro-Barter*, bounties, and trade.
2. **Everything In-Game:** Never build external out-of-game menus. Every feature (Cloud-Save/Scoreboard, Jukebox, Infusions, Companions, Endless Rift, Market Terrace) must live as an interactive station/terminal/NPC inside the game world.
3. **Backward-Compatible Saves:** Current `SAVE_VERSION = 11` in `src/systems/gameState.ts`. Any new field in `SaveData` (`src/types.ts`) must be optional (`?`) and safely defaulted in `GameState.load()`.
4. **Firebase Config Policy:** Public Firebase web config for `starlighter-15b1f` intentionally lives in `src/services/firebaseConfig.ts` (with `VITE_FIREBASE_*` env override support) because Vercel Free does not allow env var configuration. Security is enforced server-side via `firestore.rules` + Firebase Authorized Domains.
5. **Strict TypeScript:** `tsconfig.json` enforces `verbatimModuleSyntax`, `erasableSyntaxOnly`, `noUnusedLocals`, and `noUnusedParameters`. Always use `import type` for type-only imports.
6. **Mandatory Verification Before Every Push:**
   - **Code-/Spiel-Änderungen (`src/`, `scripts/`, `tests/`, `public/art/sprites/`):** `npm run verify` (`build` + `check:invariants` + `check:sprites` + Playwright-Tests) → 0 Fehler, plus Screenshots in `tests/out/` **visuell prüfen**, bevor auf `origin main` gepusht wird.
   - **Reine Doku- oder Roh-Asset-Commits (`*.md`, `art_source/**`):** `npm run check:invariants` + `npm run check:sprites` + visuelle Prüfung jedes neuen PNGs per `view_file` (weißer Hintergrund, saubere Zellentrennung, keine Fransen/Texte/Linien).
7. **Fehlende Sprites melden & priorisiert einreihen:** Legst du einen prozeduralen Fallback / Platzhalter oder ein neues geplantes M11-Sheet anstelle eines Sprites an (nur noch, wenn das Bild nicht sofort per `npm run art:gen` erzeugt werden kann oder Antigravity es übernimmt — Regel 14/15), dann **musst** du (a) bei optionalen Sprites den Sprite-Key in `M10_OPTIONAL_SPRITES` (bzw. dem passenden optionalen Block in `artLoader.ts`) registrieren, damit `npm run check:sprites` ihn listet, (b) den Prompt im passenden Brief (`ART_AND_DESIGN_GUIDE.md` §7/§8 bzw. `ART_BRIEF_M11*.md`) ergänzen, (c) den Auftrag **sofort mit Priorität (`P0`–`P4`), Zielpfad und Referenzbild in [`SPRITE_QUEUE.md`](SPRITE_QUEUE.md) an der richtigen Stelle einsortieren** und (d) in `HANDOFF.md` kurz vermerken. In deiner Abschlussmeldung weist du den Projektinhaber ausdrücklich darauf hin, dass neue Sprites benötigt werden.
8. **Übergabe:** Aktualisiere am Ende jeder Sitzung das **Status-Blatt deines Bereichs in `handoff/`** (bereichsübergreifend: `HANDOFF.md`; siehe `PARALLEL_WORK.md`). **Pushen mit `npm run ship`** (merge → verify → push, nie bei Fehlern). Prüfe mit `npm run verify` (bzw. Regel 6 bei reinen Doku-/Roh-Asset-Commits), bevor du pushst (gilt für jedes Werkzeug; Claude Code liest `CLAUDE.md`, das auf diese Datei verweist; Antigravity lädt diese Datei direkt).
9. **Tag/Nacht-Schleife (M10-C):** Laden nur nachts; Run am Tag → danach Nacht; Nacht-Run → danach Tag (Ladenschicht fällt aus); Koje nur nachts. Zeitwechsel laufen **nur** über `GameState.startNight()` / `startDay()` — nie `timeOfDay` direkt setzen. Die Wochen-Prüfung ändert die Zeit nie.
10. **Balancing zentral (M10-C):** Preise, Boss-HP, Rift-Faktoren, Waffen-Sperren, Schild-Werte stehen in `src/data/balance.ts`. Nach Änderungen `npm test -- m10cp8 m10cp10` (Boss-Kampfdauer, Prüfung) laufen lassen und `tests/out/economy.json` ansehen.
11. **Boss-Mindeststandard (M11):** Jeder Boss braucht mindestens das Niveau von Kern-Wächter/Krall — Details `BOSS_ANIMATION_PLAN.md` §1 (D1–D15): eigene Posen je Angriffsabschnitt, weiche Übergänge, **sichtbare Angriffsgrafik je Attacke** (nicht nur Telegraph-Kreis), **Beschädigungsstufen** (≥ 4 Stufen über die HP-Spanne + kritisch < 15 %), Körper ohne schwebende Teile, Beine/Unterkörper reagieren auf Angriffe. Was dafür an Sprites fehlt, sofort mit hoher Priorität in `SPRITE_QUEUE.md` eintragen (Regel 7); beim Anlegen neuer Boss-Rigs (`SPRITE_QUEUE.md` P4) gehört das in die Zellenliste.
12. **Gegner-Mindeststandard (M11):** Jeder normale Gegner-Rig erfüllt G1–G10 (`BOSS_ANIMATION_PLAN.md` §4): vollständiges Rig, sicherer Rückfall aufs alte Sprite, eigener Lauf-/Schwebe-Rhythmus, Angriff in 3 Abschnitten mit weichen Übergängen, Treffer-Reaktion, Tod, rein optisch (keine Hitbox-/Schadensänderung), eigener Test + `handoff/enemy_<kind>.md`. Beschädigungsstufen/Phase 2 sind nur für Bosse Pflicht (Regel 11).
13. **Sektor-Endbosse & Sprite-Bedarf (M12):** Ebene-III-Bosse (letzter Boss vor dem nächsten Sektor) sind **in die Map integrierte Arena-Bosse** (scrollende Großarena, Boss in Wand/Boden verankert, ≥ 3 Phasen mit Arena-Änderung, Schwachstellen, Belohnung Trophäen-Relikt + Waffen-Arten-Freischaltung + Hub-Trophäe, nie Credits) — Fertig-Definition A1–A10 in `MILESTONE_12_ARCHITECTURE.md`; **keine** bloß vergrößerten oder „stärkeren Duplikate“ normaler Bosse. Bossräume und neue Gegner brauchen **viele Sprites — das ist gewollt**: großzügig planen, jedes fehlende Bild sofort in `SPRITE_QUEUE.md` (Regel 7), bis dahin Fallback. Jeder neue Gegner/Boss/Bossraum durchläuft die 8 Stufen aus [`BOSS_ENEMY_PIPELINE.md`](BOSS_ENEMY_PIPELINE.md) (Steckbrief → Zustandstabelle → Sprite-Liste → Pilot-Sheet → Import → Posen → Checkliste → Abnahme).
14. **Neue Sprite-Sheets sind der Standardweg, nicht der Notfall (gilt für alle Agenten und für **jede** Arbeit — neue Features, Umbauten, Verbesserungen, nicht nur Rigging):** Bei jeder Aufgabe prüfen, ob neue Sprites sie **schöner** machen (Station/Prop im Hub, NPC, Item-Icon, UI-Element, Effekt, Hintergrund, Boss, Gegner) — wenn ja, Sprites einplanen und erzeugen statt nur prozedural zu zeichnen oder Vorhandenes umzufärben. Wenn eine Pose, ein Angriff, eine Arena oder ein Effekt mit den vorhandenen Bildern nicht gut aussieht, technisch nicht passt oder dem Projektinhaber nicht gefällt, wird **ein neues oder ersetzendes Sheet bestellt** — nicht mit Code-Tricks (Drehen/Strecken/Tönen einzelner Bilder) überbrückt. **Nicht an Bild-Credits sparen**, solange es der Qualität dient: der Projektinhaber hat ausreichend Gemini-Guthaben. Ablauf: neue Zeile in `SPRITE_QUEUE.md` (neue ID, Grund + Referenz; bei Ersatz *„ersetzt `<datei>` — Grund: …“*), bis zur Lieferung Fallback bzw. altes Bild. Details: `SPRITE_QUEUE.md` §0 und `BOSS_ENEMY_PIPELINE.md` §0.
15. **Direkt-Generierung aus Chats (`npm run art:gen`, jedes Werkzeug mit Gemini-Key — Claude-Chats, Codex, Cursor …):** Claude-Code-Chats dürfen Sprites/Sheets, die ihre **laufende Aufgabe** braucht oder spürbar schöner macht (neues Feature, Umbau, Verbesserung, Rigging — neu, Zusatz oder Ersatz), selbst über die Gemini-Bild-API erzeugen: `npm run art:gen -- --ref <referenz.png> --prompt-file <datei> --out art_source/_raw/<name>.png [--sheet-out <zielpfad>]` (`scripts/gen-sheet.py`, `--check-key` = Key prüfen, 0 Kosten) (Key kommt in Cloud-Sessions automatisch über das Network Secret „Google AI Studio Key“, Header `x-goog-api-key`; in Antigravity aus `~/.config/starlighter/gemini_api_key` — **nie** einen Key ins Repo oder in den Chat). Pflicht: zuerst eigene Queue-Zeile in `SPRITE_QUEUE.md` mit Status `[~]` *„in Arbeit: <chat/bereich>“* (verhindert Doppelarbeit), Ergebnis per Read/`view_file` ansehen, `art:check` ok, dann `[x]`. **Aufteilung:** Die bestehende Liste (offene `[ ]`-Einträge) arbeitet **Antigravity/Gemini** ab; Claude-Chats generieren nur, was sie selbst gerade blockiert.
16. **Biom-passende Boden-Effekte (M11/M12):** Gegner und Bosse treten auch in fremden Sektoren auf (Riss-Kammern, ∞ Spirale, Omega-Anomalie, künftige Challenges). Effekte, die **am Boden** entstehen oder liegen (Einschläge, Risse, Krater, Staub, Brandflecken, Trümmer, Tod-Rückstände), müssen zum Boden des **aktuellen Raums** passen: eigenes Sheet `<id>_ground.png` mit Varianten S1–S5, Auswahl nach Raum-Biom (`riftSector` → `floor.visualSector` → `currentSector`), Fallback = Heimat-Variante + Tönung und Bestellung in `SPRITE_QUEUE.md`. Körper-Effekte (Funken, Sporen, Laser) bleiben ein Sheet. Liste der fremden Auftritte + Format: `BOSS_ENEMY_PIPELINE.md` §5; Checklisten-Punkte G10/D15. **Geplant (Entscheidungen liegen vor, Umsetzung erst auf Startsignal):** dezente NG+-Aura für alle Wesen, eigenes Spiralen-Biom mit eigenem Hintergrund, Echo-Varianten mit neuen Attacken — `BOSS_ENEMY_PIPELINE.md` §5b, `SPRITE_QUEUE.md` (Abschnitt „NG+ & Spirale“, P4-01…06); bis zum Startsignal nichts umsetzen/generieren.
17. **Durchhalten bis „fertig“ (gilt für jede Arbeit mit Checkliste):** Ein Chat hört **nicht** nach dem ersten lauffähigen Stand auf, sondern arbeitet seine Checkliste (G1–G10 Gegner / D1–D15 Bosse / A1–A10 Arena, `BOSS_ENEMY_PIPELINE.md` Stufen 1–8) **Punkt für Punkt ab, bis jeder Punkt erfüllt und mit Nachweis im Status-Blatt abgehakt ist** — fehlende Sprites werden dabei selbst erzeugt oder bestellt (Regel 14/15), nicht umgangen. Nach jedem Teilschritt: Checkliste im Status-Blatt aktualisieren, committen, `npm run ship`, dann **sofort den nächsten offenen Punkt** angehen. Erlaubte Gründe anzuhalten (dann **ausdrücklich melden**, nicht stillschweigend aufhören): (a) alle Punkte erfüllt → Abschlussmeldung mit Nachweisliste; (b) **Abnahme durch den Projektinhaber im echten Spiel** (Stufe 8) steht aus; (c) ein **STOP-GATE** oder `[~]`-Eintrag in `SPRITE_QUEUE.md` blockiert; (d) Bild-Quota/API nicht erreichbar (Rest der Punkte ohne Bild weiterführen, Bestellung eintragen); (e) eine **Entscheidung des Inhabers** nötig ist (Frage stellen, bis dahin an anderen Punkten weiterarbeiten). **Jederzeit abbruchsicher arbeiten (Credits/Limit können ohne Vorwarnung enden, ein anderes Werkzeug — z. B. Antigravity/Gemini — muss nahtlos übernehmen können):** (1) **früh und oft pushen** — nach jedem abgeschlossenen Teilschritt `npm run ship`, spätestens alle ~30–45 Min. oder vor jedem größeren/riskanten Schritt; nie viel Arbeit ungepusht liegen lassen. (2) Lässt `ship` sich wegen eines roten Tests/Konflikts nicht abschließen, trotzdem sofort den Arbeitsstand auf den eigenen Branch sichern (`git push origin HEAD`, Commit-Text `WIP: …`) und den Blocker im Status-Blatt notieren — verloren gehen darf nichts. (3) Das Status-Blatt (`handoff/…`) ist **immer so aktuell**, dass ein fremdes Werkzeug ohne Rückfrage weitermachen kann: Checkliste (✅/⬜), bei jedem ⬜ der **konkrete nächste Schritt** (Datei, Funktion, Befehl), laufende `[~]`-Queue-Einträge, bekannte Fehler. Diese Aktualisierung gehört in **jeden** Push-Commit. (4) Kündigt sich das Ende an (Warnung zu Limit/Credits, lange Sitzung): sofort ship/WIP-Push + Status-Blatt, dann erst weiterarbeiten. Antigravity/Gemini nimmt bei Übernahme `HANDOFF.md` + das Status-Blatt + `SPRITE_QUEUE.md` und arbeitet die ⬜-Zeilen weiter ab.

18. **Ein Besitzer pro Bereich (Claim-Regel, gilt für alle Agenten & Chats):** Vor jeder Arbeit `git fetch`, [`handoff/README.md`](handoff/README.md) (Claim-Liste) und offene `[~]`-Zeilen in `SPRITE_QUEUE.md` prüfen; ist der Bereich/die Datei belegt → nicht anfangen. Eigenen Claim vor der ersten Code-Zeile eintragen und pushen, beim Ende freigeben; Sprite-Dateinamen nur mit eigener `[~]`-Zeile. Kollisionen ohne blindes Mergen auflösen (Sicherungs-Branch, beide Ergebnisse ansehen, bessere behalten, Inhaber informieren) — Ablauf: `PARALLEL_WORK.md` §5. Praxis-Learnings in das Status-Blatt des Bereichs schreiben.

19. **Alles Gelernte sofort dokumentieren — Chatwechsel-sicher (gilt für jeden Agenten, jede Arbeit):** Jede Erkenntnis, die ein nachfolgender Chat sonst neu herausfinden müsste, wird **im selben Arbeitsschritt** ins Status-Blatt des Bereichs (`handoff/<bereich>.md`, Abschnitt „Praxis-Learnings“, fortlaufend nummeriert) geschrieben und im **selben Commit** gepusht — nicht erst am Ende: (a) Fehlerursachen & wie sie behoben wurden (z. B. „Posen am Zellraster zerschnitten“), (b) Fallen/Stolpersteine, (c) Befehle/Skripte, die funktioniert haben (Ort nennen; wiederverwendbare Skripte nach `scripts/` statt in den Scratchpad), (d) Entscheidungen des Inhabers & Maße/Werte (Pivot, Offsets, Schwellen), (e) was **bewusst nicht** gemacht wurde und warum, (f) offene Punkte mit konkretem nächsten Schritt. Allgemeingültiges (nicht bereichsspezifisch) zusätzlich in `AGENTS.md`/Pipeline-Dokument. Vor dem Ende einer Sitzung und vor jedem möglichen Abbruch gilt: Was nur in deinem Kopf steht, ist verloren.

20. **Sitzungs-Abschluss-Protokoll (Pflicht für jeden Chat/Agenten — auch bei kleinen oder abgebrochenen Aufgaben, auch wenn „nichts“ fertig wurde):** Bevor du aufhörst (oder sobald ein Limit/Credit-Ende droht), trägst du — im selben Commit, gepusht per `npm run ship` bzw. `WIP:`-Push — **zwei Dinge** ein: (1) im **Status-Blatt des Bereichs** (`handoff/<bereich>.md`): Checkliste ✅/⬜ aktualisiert, Praxis-Learnings (Regel 19), bei jedem ⬜ der konkrete nächste Schritt; (2) in `HANDOFF.md` den Block **„🔁 Letzte Sitzungen (Weiter-Protokoll)“** (neueste Zeile oben, max. 8 Zeilen behalten, ältere löschen) mit: Datum · Werkzeug/Chat · Bereich · **Erledigt** (1 Satz, Commit/Test als Nachweis) · **Nicht erledigt / Blocker** · **Nächster Schritt für den nächsten Chat** (Datei + Befehl) · offene `[~]`-Queue-Einträge · Claim in `handoff/README.md` freigegeben (ja/nein). Zweck: Der Projektinhaber kann **sofort einen frischen Chat** mit dem Startsatz aus `KI_WECHSEL.md` §0 öffnen, ohne dass dieser Code/Doku neu durchsuchen muss (spart Credits). Fehlt der Eintrag, gilt die Sitzung als nicht abgeschlossen. Letzter Satz deiner Abschlussmeldung an den Inhaber: der fertige **Startsatz für den nächsten Chat** (1–2 Zeilen, siehe Vorlage).

21. **PC first, Handy muss nutzbar sein (Inhaber-Vorgabe):** Jede neue/umgebaute UI (Menüs, Modals, HUD) wird zuerst für PC entworfen, **muss aber auch am Handy quer und hochkant benutzbar sein** (nichts abgeschnitten, alles ohne Zufallsscrollen erreichbar, Touch-Flächen ≥ ~34 px). Dafür eigene Media-Queries (PC-Layout nicht verbiegen) und vor dem Push per Playwright-Viewport `915×412`, `844×390` (quer) und `390×844` (hoch) ansehen — Vorlage: `tests/t10_save_slots.cjs`, Learning #9 in `handoff/title_screen.md`.

„Gut genug“ oder „Rest später“ ist **kein** Grund — offene Punkte stehen sonst mit Begründung in der Abschlussmeldung und im Status-Blatt.

## 4. Quick "How to Add X" Cheat Sheet
> **Bei jedem Punkt unten gilt Regel 14/15:** Wird das Feature durch eigene Sprites schöner (Prop, Icon, NPC, Effekt, UI-Grafik, Hintergrund), Sprites einplanen und per `npm run art:gen` erzeugen bzw. in `SPRITE_QUEUE.md` bestellen — prozedurale Zeichnung nur als Fallback.
- **Add a new Relic / Material:**
  1. Generate & flood-fill extract `64×64` PNG → `public/art/sprites/item_<id>.png` (auto-loaded by `artLoader.ts`!).
  2. Add `ItemDef` to `ITEMS` in `src/data/items.ts` (and `rollLootItem` / `rollRiftLootItem` if needed).
- **Add a new Weapon Infusion or Rift Mutator:**
  1. Define in `src/data/infusions.ts` + extend `InfusionId` / `RiftMutatorId` in `src/types.ts`.
  2. Wire combat behavior in `DungeonScene.ts` (`damageEnemy` / `onEnemyKilled` / `damagePlayer`), status ticks in `src/dungeon/enemyAi.ts`, and FX in `src/dungeon/dungeonRenderer.ts`.

## 6. Zusammenarbeit Antigravity ↔ Claude Code (Antigravity-Zusatz)
> Entsprechung zu `CLAUDE.md` für Antigravity-Sitzungen (diese Datei wird automatisch geladen).

1. **Sitzungsstart (immer zuerst):** `git fetch origin && git status` (und `git pull --ff-only`, falls `origin/main` voraus ist), dann [`HANDOFF.md`](HANDOFF.md) und bei Sprite-Arbeit [`SPRITE_QUEUE.md`](SPRITE_QUEUE.md) lesen. Claude Code und Antigravity pushen abwechselnd auf `main`; eine wiederaufgenommene VM kann auf einem älteren Commit stehen.
2. **Typische Aufgabenteilung:**
   - **Antigravity (`generate_image` + PIL + Repo-Commit):** Pixel-Art-Sprites, M11-Teile-Sheets (`art_source/rigs/<id>_parts.png`) sowie Pose-Set- und Gegner-Rig-Sheets (`art_source/rigs/<id>_arms_L.png`, `<kind>_rig.png`, …) — **verbindliche Reihenfolge & STOP-GATES stehen in [`SPRITE_QUEUE.md`](SPRITE_QUEUE.md)** (1-Satz-Batch-Ablauf: Skill `sprite-batch`) — sowie reguläre Code-/Doku-Aufgaben nach Bedarf.
   - **Claude Code:** Architektur-Pläne, Code-Phasen, Tests, `npm run art:import` & `npm run verify` (und Einsortieren neuer benötigter Sprites/Fallbacks in `SPRITE_QUEUE.md` gemäß §3 Regel 7).
3. **Pflicht-Workflow für generierte Bilder (`generate_image`):**
   - `generate_image` speichert zunächst nur im internen Artifact-Ordner (oft als `.jpg`) — **niemals** dort liegen lassen!
   - Bestehendes Sprite als Referenz über `ImagePaths` übergeben (z. B. `public/art/sprites/boss.png` für den Kern-Wächter); Seitenverhältnis setzen (`AspectRatio: '3:2'` für 3×2-Teile-Sheets, `'1:1'` für Einzel-Sprites).
   - **Sicht- & Rasterprüfung vor Ablage:** Per `view_file` und Python/PIL prüfen, dass alle Teile sauber in ihrer Zelle liegen, keine Rasterlinien/Texte/Schatten/Überlappungen vorhanden sind und einheitlicher Maßstab gilt. Bei 3×2-Teile-Sheets ggf. per PIL sauber ohne Skalierungsverlust in ein reines `#FFFFFF`-Raster `1536×1024` (`512×512` pro Zelle) als verlustfreies `.png` nach `art_source/rigs/<id>_parts.png` packen; fertige Einzel-Sprites nach `ART_AND_DESIGN_GUIDE.md` §3 freistellen und nach `public/art/sprites/<name>.png` legen.
   - **Credits & Durchlauf-Schleife (Qualität vor Sparen, Regel 14):** Standardmäßig arbeitet der Skill `sprite-batch` in **2er-Micro-Batches** mit automatischem Weitermachen (`Commit` + `npm run ship` nach jeder Runde), bis das Quota-Limit, ein **STOP-GATE** in `SPRITE_QUEUE.md`, die Fehler-Notbremse oder der Sicherheits-Deckel (10 Sheets) greift (oder eine vom Nutzer genannte Stückzahl erreicht ist). Bei neuen Serien immer erst die Pilot-Sheets erzeugen und **STOP-GATES** respektieren.
4. **VM-Besonderheiten (Antigravity):** `python3` mit `Pillow` und `/usr/bin/google-chrome` sind vorinstalliert. In einer frischen VM fehlt ggf. `node_modules` → für `npm run build` / `npm run verify` zuerst `npm install` (und falls Playwright-Chromium fehlt: `npx playwright install chromium`).
5. **Übergabe & Push:** Nach Abschluss (bzw. nach jeder 2er-Runde im Batch-Loop) `SPRITE_QUEUE.md` und das zuständige `handoff/`-Blatt (z. B. `handoff/enemy_sheets.md`, bereichsübergreifend `HANDOFF.md`) aktualisieren, committen und per `npm run ship` sicher auf `origin main` pushen (außer der Nutzer wünscht „nur lokal“).
